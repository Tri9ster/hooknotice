## F-01: エージェントの回答が公式仕様と違った

- **症状**: `PermissionRequest` の返し方を調査用エージェントに聞くと、`"decision": "allow|deny|defer"`
  （文字列）という形が返ってきた。`updatedPermissions` も「記載なし」とされた。
- **原因**: エージェントの要約の誤り。公式ドキュメントでは `decision` はオブジェクト
  （`{"behavior": "allow", "updatedInput": ..., "updatedPermissions": ..., "message": ..., "interrupt": ...}`）。
- **対処**: `code.claude.com/docs/en/hooks.md` を直接取得し、「PermissionRequest decision control」の節を読んで実装した。
- **教訓**: Hook の入出力のように形を間違えると黙って無視される仕様は、要約ではなく一次資料の本文で確認する。

## F-02: Hook を kill してもウィンドウが残った

- **症状**: Hook のタイムアウトを想定して `hook_notify.py` を kill したが、通知ウィンドウが残った。
- **原因**: 親の終了を「`os.getppid()` が起動時と変わったか」で判定していた。テストでは Hook をウィンドウの
  起動より先に kill したため、ウィンドウは起動時点で既に launchd（pid 1）の子になっており、ppid は最後まで変わらなかった。
- **対処**: 判定を「ppid が変わった、**または ppid が 1**」にした。
- **教訓**: 親子の生存判定は「起動した瞬間に既に孤児」というケースを考える。
  （同時に F-07 も起きており、原因の切り分けに時間がかかった。）

## F-03: 質問にも OK/キャンセルが出て、キャンセルで質問が拒否された

- **症状**: テスト中に Claude が `AskUserQuestion` で質問したところ、通知に OK/キャンセルが出た。
  ユーザーがテスト対象の通知と思ってキャンセルを押し、質問が「通知ウィンドウでユーザーが拒否しました」で拒否された。
- **原因**: `AskUserQuestion` と `ExitPlanMode` も `PermissionRequest` Hook を通る（マッチャー `*`）。
  これらは「回答そのものがユーザー入力」なので、allow / deny では答えにならない。
- **対処**: `NO_ACTION_TOOLS` を設け、この2つはボタン無しの通知を切り離して出すだけにした。
- **教訓**: マッチャー `*` の Hook は、ツール実行以外の対話的なツールにも効く。決定を返す Hook は対象を絞る。

## F-04: auto モードで許可確認が起きず、通知も出なかった

- **症状**: 実機テストで、キャンセルを押すはずのコマンドがそのまま実行された。
- **原因**: セッションが auto モードで、安全と判断された操作は許可確認なしで実行される。
  許可確認が無ければ `PermissionRequest` Hook も発火しない（最初のテストで確認が出たのは偶然）。
- **対処**: ユーザーに manual（default）モードへ切り替えてもらって再テストした。README にも明記した。
- **教訓**: 許可まわりのテストは、先に許可モードを確認する。

## F-05: コマンド欄クリックのテストで、拒否のはずが実行された

- **症状**: 「コマンド欄をクリック → ターミナル側で拒否」のテストで、コマンドが実行された。
- **原因**: 不明。ユーザーの希望でやり直したテストでは、想定どおり拒否された。
  誤操作（ターミナル側で許可を選んだ）の可能性があるが、確認できていない。
- **対処**: なし（再現していない）。
- **教訓**: 期待と違う結果が出たら、やり直す前に「何を押したか」を先に聞いて記録する。

## F-06: 配布先で「OK を押しても許可されない」

- **症状**: 配布先から「OK ボタンを押しても、VS Code に表示されている OK ボタンが押されない」との報告。
- **原因**: 未確認。有力なのは、配布先の `settings.json` で許可待ちの Hook が `"async": true` のまま
  （async の出力は無視されるため、通知と OK ボタンは出るが何も起きない）。ほかに、設定変更後の再起動漏れ、
  別の `PermissionRequest` Hook や deny / ask ルールの影響、「ツールは実行されたがダイアログの表示が残った」だけ、が考えられる。
- **対処**: README のトラブルシューティングに確認手順を追記し、zip を作り直した。
- **教訓**: 配布物は「コード」と「設定（hooks.json）」の組で意味を持つ。仕組みを変えたときは、受け取った人が
  古い設定のままになる可能性を README で先に案内する。
- **未確認**: こちらの環境で、Hook が allow を返したときに VS Code 側のダイアログが消えるかどうか。

## F-07: 動作確認の pgrep が別の通知に誤って一致した

- **症状**: `pgrep -f "notify_window.py.*--actions"` でテスト用ウィンドウを探したら、無関係の通知が一致した。
- **原因**: 以前から表示されていた ExitPlanMode の通知の本文（コマンドライン引数）に、計画の文章として
  `--actions` という文字列が含まれていた。
- **対処**: テスト用の通知の説明文に一意な文字列（「テストkill」など）を入れて、それで探した。
- **教訓**: コマンドライン引数に任意の本文を載せるプロセスを pgrep で探すときは、一意な目印を入れる。

## F-08: 実装中に未定義の関数を呼ぶコードを書いた

- **症状**: ライトの縁取りで `border_path(self.rect())` という存在しない関数を呼ぶコードを書いた。
- **原因**: 置換スクリプトに仮の名前を書いたまま適用した。
- **対処**: import 確認の段階で気づき、`drawRoundedRect` を 0.5px 内側に描く実装に直した。
- **教訓**: 一括置換のスクリプトに仮の名前を書かない。適用後すぐに `py_compile` と描画を行う。

## F-09: テーマ化でダークの高さが 133 → 129px に変わった

- **症状**: 配色をテーマ化した後、ダークの通知が変更前より 4px 低くなった。
- **原因**: スタイルシートの適用（`_apply_theme`）を `_fit_height` の後に移してしまった。高さ計算の時点で
  フォントサイズ（11〜13px の指定）が反映されておらず、既定フォントで計算していた。
- **対処**: テーマの適用をレイアウト構築の前（元のスタイルシートと同じ位置）に戻した。
  そのためにハイライト色の乱数（`_init_highlight_params`）とグラデーションの座標（`_init_gradient_params`）を分けた。
- **教訓**: Qt で高さを自前で計算するときは、スタイルシートを先に当てる。見た目の回帰は画像のバイト比較で検出できる。

## F-10: 修正後も差分が出た（実は古い画像を比較していた）

- **症状**: F-09 を直した後も、比較で高さが 129px のままだった。
- **原因**: 描画スクリプトを `hooknotice/` 以外のディレクトリで実行し、`import notify_window` に失敗していた。
  エラーを `2>/dev/null` で捨てていたため気づかず、前回の古い画像を比較していた。
  部品ごとのサイズを新旧で出力して、両方 133px であることから判明した。
- **対処**: `hooknotice/` で実行し、古い画像を消してから描画し直した。変更前とバイト単位で同一になった。
- **教訓**: 検証スクリプトの stderr を丸ごと捨てない（捨てるなら既知の警告だけを grep -v で除く）。
  出力ファイルは作り直す前に消す。

## F-11: 仕様書の「暗いブロック」がライトで不正確になった

- **症状**: 仕様書 5章の「等幅フォントの暗いブロック」が、ライト配色では当てはまらなくなった。
- **対処**: 「等幅フォントの背景付きブロック」に直した。
- **教訓**: 見た目の変更をしたら、仕様書の見た目の描写も検索して直す。

## F-12: `claude` が PATH に無かった

- **症状**: 解説の生成に使う `claude` コマンドが見つからなかった。
- **原因**: この環境の Claude Code は VS Code 拡張のみで、CLI は拡張内
  （`~/.vscode/extensions/anthropic.claude-code-<版>-darwin-arm64/resources/native-binary/claude`）にしか無い。
  バージョンごとにパスが変わる。
- **対処**: Hook に渡される環境変数 `CLAUDE_CODE_EXECPATH`（実行中の Claude Code のバイナリ）を優先し、
  無ければ PATH の `claude` を使う。どちらも無ければボタンを出さない。
- **教訓**: Hook から Claude Code 自身を呼ぶときは、PATH ではなく `CLAUDE_CODE_EXECPATH` を使う。

## F-13: `--bare` は OAuth を読まず使えない

- **症状**: Hook を読まない軽い起動方法として `--bare` を検討したが、ヘルプに「Anthropic auth is strictly
  ANTHROPIC_API_KEY or apiKeyHelper（OAuth and keychain are never read）」とあった。
- **原因**: サブスクリプション（OAuth）でログインしている環境では認証できない。
- **対処**: `--setting-sources ""`（ユーザー設定の Hook を読まない）と環境変数 `HOOKNOTICE_DISABLED=1` で代替した。
- **教訓**: CLI のオプションは、副作用（認証の読み込み）までヘルプ全文で確認する。

## F-14: `claude -p` が stdin 待ちで3秒遅れた

- **症状**: 試しに実行すると「Warning: no stdin data received in 3s, proceeding without it」が出た。
- **原因**: `-p` は stdin からの入力も受け付けるため、stdin が開いていると3秒待つ。
- **対処**: `QProcess.start()` の直後に `closeWriteChannel()` を呼ぶ。
- **教訓**: 子プロセスに stdin を渡さないときは明示的に閉じる。

## F-15: 解説を表示してもカードが伸びなかった

- **症状**: 解説欄（275px）を追加しても、カードは 146px のままだった。
- **原因**: 表示済みのウィンドウに後から追加した子ウィジェットは、`show()` を呼ぶまで非表示のまま。
  非表示のウィジェットはレイアウトの高さ計算に含まれない。
- **対処**: 解説欄を `insertWidget` した直後に `view.show()` を呼ぶ。
- **教訓**: Qt で表示後に子を追加したら `show()` する（構築時に追加した子は親の `show()` で表示されるので気づきにくい）。

## F-16: 解説中のコードが等幅にならず、見出し・字下げも大きかった

- **症状**: `setMarkdown()` の表示で、`` `code` `` やコードブロックが本文と同じフォントになり区別できなかった。
  見出しが大きく、箇条書きの字下げも深く、340px のカードでは読みにくかった。
- **原因**: Qt の Markdown 取り込みはコードに「等幅」の属性（`fontFixedPitch`）を付けるだけで、具体的な
  フォントは環境任せ。見出しサイズや字下げ幅も広い画面向けの既定値。
- **対処**: `_polish_markdown` を追加。ブロックと断片を走査し、見出しは px 指定で 12〜14px、等幅属性の断片と
  コードブロック（`BlockCodeFence`）は Menlo にして背景を付け、`setIndentWidth(14)` で字下げを浅くした。
  外観切り替え時に背景色を合わせ直すため、表示中の Markdown を保持して再適用する。
- **教訓**: Qt の Markdown 表示をそのまま狭い UI に使うと崩れる。取り込み後にドキュメントの書式を調整する。

## F-17: コードブロックの長い行が右端で切れた

- **症状**: 実際の解説で、長いコマンドのコードブロックが右端で切れた（「README.」で途切れる）。
- **原因**: Qt はコードブロックに `NonBreakableLines`（折り返し禁止）を設定する。解説欄は横スクロールを
  無効にしているため、はみ出した分が見えない。
- **対処**: `_polish_markdown` でコードブロックの `setNonBreakableLines(False)` を指定して折り返す。
- **教訓**: 短い固定の Markdown では再現しなかった。実際の生成結果でも描画を確認する。

## F-18: 計画の大見出し（h1）が極端に大きく表示された

- **症状**: 計画（ExitPlanMode）を Markdown で表示すると、先頭の `#` 見出しが 20px 以上の大きさで3行に折り返された。
- **原因**: Qt の Markdown 取り込みは、見出しに文字サイズの段階（`QTextFormat.FontSizeAdjustment`、h1 は +3、h3 は +1）を付ける。
  `_polish_markdown` で `FontPixelSize` を指定しても、この段階が上乗せされていた。解説では h3・h4 しか使わず、
  差が小さかったので気づかなかった。
- **対処**: 見出しの書式で `FontSizeAdjustment` を 0 に戻す。
- **教訓**: 書式を上書きするときは、実際に付いている属性を調べる（`charFormat().property(...)` を出力して確認した）。
  見出しの全レベルを含む入力で描画を確認する。

## F-19: Markdown 中のコードの文字が本文より大きかった

- **症状**: 計画のコードブロックとインラインコードの文字が、本文（11px）より大きく表示された。
- **原因**: 等幅にするときにフォント名（Menlo）だけを指定し、文字の大きさは Qt の既定のままだった。
- **対処**: コード部分にも `FontPixelSize` 11 を指定した（解説欄にも効く）。
- **教訓**: フォントを差し替えるときは大きさもそろえる。

## F-20: 計画承認の通知で承認ボタンを押しても Claude Code が進まなかった

- **症状**: 計画承認（ExitPlanMode）の通知で「自動モードで承認」「都度確認で承認」「編集を自動許可で承認」の
  どれを押しても、通知は閉じるのに Claude Code の承認ダイアログが残り、先に進まなかった。
  「計画を続ける」（拒否）だけは効いた。テスト用の入力で出した通知では、返す JSON の形が正しかったので気づかなかった。
- **調べ方**: 一時ログ（`debug.log`）で、クリック → ウィンドウの結果 → Hook が返した決定 を1行ずつ記録した。
  クリックは届き、Hook も `behavior: "allow"` を出力していた。モード切り替えの無い「都度確認」でも同じだったので、
  `setMode: auto` が原因ではないことも分かった。
- **原因**: ExitPlanMode と AskUserQuestion は、ユーザーの回答そのものが入力になるツールで、allow だけでは
  Claude Code に採用されない。allow に `updatedInput` を組にする必要がある（公式の hooks ドキュメントに記載）。
  選択肢の質問は最初から `updatedInput` を返していたが、計画承認には付けていなかった。
- **対処**: 計画承認の allow に、Hook に渡された `tool_input`（`plan` / `planFilePath`）をそのまま `updatedInput` として付けた。
  実機で「自動モードで承認」から計画モードを抜けられることを確認した。
- **教訓**: Hook の決定は「JSON の形が正しい」だけでは足りず、実際の Claude Code が採用するかを実機で確かめる。
  特殊なツール（AskUserQuestion / ExitPlanMode）は、公式ドキュメントのツール別の注意書きを先に読む。
  切り分けには、クリックから Claude Code に返す決定までを記録する一時ログが有効だった。
  なお、計画モード中は修正を書き込めないため、通知が効かない状態で計画承認を待つと行き詰まる。
  その場合は通知を ✕ で閉じて VS Code 側で承認するか、自分で計画モードを解除する。

## F-21: 許可待ちに6秒以内に答えても通知が出た

- **症状**: 許可待ちに VS Code 側ですぐ答えても、約6秒後に通知ウィンドウが出た。
- **調べ方**: 一時ログで、Hook の開始・0.5 秒ごとの親プロセスと stdout の状態・受け取ったシグナルを記録した。
  約4秒で許可してコマンドが実行された後も、Hook はシグナルを受けず6秒の待ちを最後まで続けていた。
- **原因**: 「待つ間にターミナル側で答えると Claude Code が Hook を終了させる」という前提が誤りだった。
  以前の検証は、Hook を手で kill するテスト入力でしか確かめていなかった。公式ドキュメントにもこの挙動の記載は無い。
  PermissionRequest の入力には `tool_use_id` も無い。
- **対処**: 会話の記録（`transcript_path`）で、同じツール名・入力の呼び出しに結果が書かれたかを確かめるようにした。
  最初の実装は Hook の開始時にだけ呼び出しを探したため、実機では見つからず効かなかった（呼び出しの書き込みが
  Hook の開始より遅れる）。待つ間も探し続けるように直した。
- **教訓**: Claude Code の挙動を前提にするときは、テスト入力ではなく実機で確かめる。会話の記録は書き込みが遅れることがある。

## F-22: 設定画面の補足の文言とチェックボックスが見切れた

- **症状**: 設定画面の「表示」で、灰色の補足の文言が上下で切れて読めなかった（言語・待ち時間・読む速さ・アプリが前面のとき）。
  「アプリが前面のとき」のチェックボックスの文言は右端で切れていた。英語ではさらにひどかった。
- **原因**: 3つが重なっていた。
  1. `setMinimumWidth(520)` がレイアウトの計算した幅の下限（日本語 604px、英語 711px）を上書きし、
     `resize(560, 720)` でそれより狭いウィンドウになっていた。チェックボックスは折り返さないので右が切れた。
  2. macOS のスタイルでは `QFormLayout` の入力欄の列が広がらない（`FieldsStayAtSizeHint`）。折り返すラベルが
     狭い幅に押し込まれ、行数が増えた。
  3. ウィンドウの高さの下限は、折り返すラベルを折り返す前の幅で計算した値になる。実際の幅で増えた行の分は
     確保されず、縮められるほうの「表示」が削られた。
- **対処**: 補足を入力欄の下に移し、`AllNonFixedFieldsGrow` で列を広げ、`setMinimumWidth` をやめた。
  「表示」の高さの下限は `heightForWidth` で今の幅に合わせて設定する（`_fit_display_group`）。
- **教訓**: 設定画面に行を足したら、日英の両方で画像にして確かめる。折り返すラベル（`setWordWrap`）を入れた
  レイアウトは、高さの下限を Qt が正しく出さないことがある。レイアウトの下限より小さい `setMinimumWidth` を書かない。
